# 全画面の自動見た目比較(visual-regress)設計書

2026-10-26 / ブランチ milspec-polish / 置き場所 `scripts/visual-regress/`

## 1. なぜ作るか

この後、大量のリファクタが続く(整頓 ④共同編集・⑥ハウジングの窓・⑤Timeline.tsx 切り分け・列固定 Task 5〜、⑦の残り)。
画面はテーマ 4 種・PC/スマホ・言語ちがいがあり、窓も約 85 ある。変更のたびに masaya に「全部見てください」と頼むのは不可能(masaya 発言 2026-10-26)。
だから、確認を人の手作業にせず**仕組みとして毎回同じ手順で回す**。

masaya の要望(2026-10-26)は次のとおり。
- 今後機能を足すときや直すときも、ミスが起きにくい作りにする
- 今後作るものもその決まりに沿わせる

このため、道具を作って終わりにはしない。**新しい画面・窓が自動でカタログ入りを強制される**ところまでを範囲にする。

## 2. 成功の形

- リファクタの前後で 1 コマンド回すと、**差が出た画面だけ**の報告ページができる。
- Claude が差を 1 件ずつ「意図した変化 / 崩れ / 判断つかず」に仕分ける。masaya は仕分け済みの一覧だけを見る。
- 何も変えていないのに差が出ることは原則ゼロ(誤報だらけでは誰も見なくなる)。
- 全部回しても 15 分以内。絞り込めば 1〜2 分。

## 3. やらないこと / 失敗の定義

- **やらない**: 本番サーバーに対する撮影(従量課金と本番データの変動がある)。CI への組み込み(当面ローカルで回す)。動き・アニメーションの比較(止めた最終状態だけを撮る。動きは既存の `scripts/sticky-scroll/frame-sync.mjs` や実機確認の担当)。
- **失敗**(動いても失敗とみなす):
  - 何もしていないのに毎回差が出る
  - 崩れを「差なし」で見逃す
  - 時間がかかりすぎて回さなくなる
  - 新しい窓を足したときにカタログ登録を忘れても気づけない

## 4. 全体の流れ

```
1) 撮る: 変更前と変更後を同じ時間帯に撮る(下の A/B 方式)
2) 比べる: 画面ごとに画素比較 → 許容を超えたものだけ「差あり」
3) 報告: 差ありの画面だけ 前 / 後 / 差分の色塗り を並べた HTML(ローカル)
4) 仕分け: Claude が報告を見て verdicts.json に「意図/崩れ/不明+理由」を書く → 報告ページに反映
5) masaya は仕分け済みの一覧(崩れ・不明が上)だけ見る
```

### 4.1 A/B 方式(決定・Claude の判断)

保存しておいた古い基準と比べる方式は採らない。**変更前のコミットと今の作業ツリーを、同じ実行の中で続けて撮る**。

- 理由 1: 基準が古くなると、ブラウザ更新・フォント・マスターデータの変化が全部「差」になり誤報が増える。
- 理由 2: 既存の性能測定でも「同じ時間帯に交互に測る A/B」が正解だった(列固定の台帳 Ruling P14)。
- 実装の形: `--base=<コミット>`(既定 = 作業ブランチの分岐点、または `HEAD`)の一時 worktree を作り、dev サーバーを 2 つ(別ポート)立てて撮る。`node_modules` は元の作業ツリーのものを共有する(junction)。`package.json` が違う場合は警告して止める。
- 道具そのもの(`scripts/visual-regress/`)は**常に今の作業ツリーのもの**を使う(base 側のアプリだけ古くする)。
- 補助として `--save-as=<名前>` / `--compare=<名前>` の保存基準モードも持つ(同じ画面を何度も撮り直して直すとき用)。既定は A/B。

## 5. 毎回同じ絵にする仕組み(最重要)

調査結果(2026-10-26)では、次の理由で何もしないと毎回絵が変わる。
- dev サーバーの `/api/*` は本番 `https://lopoly.app` に転送される(`vite.config.ts:125-137`)ので、本番の実データが映る。
- マスターデータは、キャッシュがあっても必ず Firestore に dataVersion を聞きに行く(`useMasterData.ts:101`)。
- ハウジング一覧は `Math.random` の種で並ぶ(`useHousingListOrderStore.ts:31`)。
- LP の時計、NEW リボン、MIL-SPEC の DTG 時計・ノイズ canvas(`armor/defs.ts:6-20`)が時刻や乱数で変わる。

これに対して、次のように固定する。

| 対象 | 固定のしかた |
|---|---|
| Firestore / Firebase Auth / Analytics(`*.googleapis.com` `*.firebaseio.com` など) | `page.route` で全部遮断する。マスターデータは例外処理で同梱の静的データに落ちる(`useMasterData.ts:143-156`)。遮断しても表示まで到達することは調査で確認済み(描画を止める await が無い)。**静的データに落ちきるまで待ってから撮る**(落ちる前に撮ると途中の絵になる) |
| `/api/*` | `page.route` で**見本 JSON**を返す。見本は `scripts/visual-regress/fixtures/api/` に置く**人工データ**(実ユーザーのデータは入れない=公開リポ)。未登録の `/api` 呼び出しは失敗扱いでログに出し、その画面を「撮影失敗」にする(黙って本番へ流さない) |
| 画像・動画(`lopoly.app/housing-media`, pbs.twimg.com, ytimg, media.lopoly.app, firebasestorage) | 決まった見本画像(リポ内に生成スクリプトで作る単色+番号入りの画像)に差し替える。YouTube iframe は遮断する |
| Google Fonts | 初回だけ取得して `scripts/visual-regress/.cache/`(gitignore)に保存し、以後はそこから返す |
| WebSocket(collab) | 遮断する。collab 画面は段階 2 以降(§8) |
| 時刻 | `page.clock` で固定時刻(例 2026-10-01 12:00 JST)にする。NEW の判定もこの時刻を基準にする |
| 乱数 | addInitScript で `Math.random` を固定の種の擬似乱数に差し替える |
| 動き | 既存 `shots.mjs` の `freeze()` を共通部品に移して使う(reduced motion・transition 無効・有限アニメは終点へ・無限アニメは停止・video は 0 秒で停止)。framer-motion の登場アニメの完了を待つ |
| 初回だけ出る窓 | `tutorial-storage` を完了状態に、`lopo_mobile_guide_completed='true'`、`lopo.popularDisplayConsent='1'` を設定する(調査 §0) |

検出力は 2 方向で確かめる。
- **合格条件 1(誤報ゼロ)**: 同じコミットを A/B で 3 回撮って、全画面で差ゼロ。差が出る画面は原因を潰す。どうしても揺れるものだけ、画面ごとの許容(既存 shots.mjs のブロック方式)を持つ。
- **合格条件 2(見逃さない)**: `--inject-css` で 2〜3px ずらす・色を 1 段変える・要素を 1 つ消す。どれも「差あり」になること。

## 6. 画面カタログ

`scripts/visual-regress/catalog/` に、ページ単位のファイルで宣言する(データとして書き、撮影の処理は共通エンジンが持つ)。1 項目に持たせるもの:

- `id`(例 `miti/party-settings`)
- `route`(URL)
- `storage`(localStorage に入れる見本データ。軽減表は既存 `scripts/milspec-sp2/_fixture.mjs` / `shots.mjs` の形を再利用)
- `api`(この画面が使う見本 JSON の名前)
- `open`(窓を開く手順: 押すボタン・キー・CustomEvent・store 直接操作。調査で分かった開き方を使う)
- `ready`(撮ってよい合図: 窓の目印 `[data-modal-shell]` / `role="dialog"` / 個別のセレクタ)
- `axes`(撮る組み合わせ、次の §6.1)
- `clip`(画面全体 or 窓だけ)

### 6.1 撮る組み合わせ(決定・Claude の判断)

全部の窓を全部の組み合わせで撮ると数千枚になる。そこで「ページは広く、窓は代表で」撮る。

| 種類 | 画面幅 | テーマ | 言語 |
|---|---|---|---|
| /miti の**ページ** | 1489(本人)/ 1920(多数派)/ 390 スマホ | 標準ダーク・標準ライト・MIL-SPEC ダーク・MIL-SPEC ライト(スマホは MIL-SPEC 無しなので標準 2 種) | ja / en |
| /miti の**窓** | 1489 / 390(スマホに無い窓は 1489 のみ) | 標準ダーク・標準ライト・MIL-SPEC ダーク(方針 B=窓は標準の見た目なので、MIL-SPEC は 1 種で足りる) | ja(文字が多い窓は en も) |
| /housing のページと窓 | 1489 / 390 | ハウジングのライト・ダーク | ja / en |
| LP・/about・/privacy・/terms・/stgy | 1489 / 390 | ダーク・ライト | ja / en |

- 撮影は 1489 = DSR 2.58、1920 = DSR 2、390 = DSR 3(既存道具と同じ)。
- 目安の枚数は約 600〜800 枚。並列 3〜4 で 15 分以内を目標にする。超える場合は窓の言語を ja のみに減らす。
- `--only=<文字>` で id や組み合わせを絞り、開発中は 1〜2 分で回せるようにする。

### 6.2 段階(どこまでを最初に作るか)

- **段階 1(最初に作る)**: エンジン一式(§5 の固定・A/B・比較・報告・仕分け)と、**ログイン不要で開けるもの全部**を入れる。
  - LP・法務ページ・/stgy
  - /miti の標準シェルと MIL-SPEC シェル(PC・スマホ)と、ログイン不要の窓
  - /housing の探す・お気に入り・ツアー・詳細・ハウジンガーページと、ログイン不要の窓
- **段階 2**: ログイン必須の画面と窓。dev 専用の「偽ログイン」を用意する(dev のときだけ、store にテスト用の利用者を入れる口。本番ビルドには含めない)。対象は次のとおり。
  - アカウント
  - 報告
  - マイページ
  - 登録
  - 共有の選択
  - 共同編集の主催パネル
  - 通知
  - 管理画面(既存の `npm run dev:admin` の偽管理者を使い、足りない API は見本 JSON で補う)
- **段階 3**: 共同編集の画面(WebSocket の見本を作る)と、ドラッグ中など途中状態の絵。

## 7. 比較と報告

- 比較は既存 `shots.mjs` のブロック方式(8×8 画素のブロックの平均色差)を共通部品に移して使う。§5 で固定しきれれば許容はほぼゼロになる想定。
- 報告: `scripts/visual-regress/.out/<実行名>/report.html`(gitignore)。
  - 差ありの画面だけを、前 / 後 / 差分(違うブロックを色で塗る)の 3 枚で並べる。
  - 撮影失敗の画面は「撮れなかった」として必ず一覧に出す(黙って抜けない)。
  - 仕分けが付いていれば「崩れ → 不明 → 意図した変化」の順に並べ、理由の一文を添える。
- 仕分け: Claude が `verdicts.json`(`{id: {verdict: 'intended'|'broken'|'unsure', reason}}`)を書き、報告を作り直す。**Claude が画像を見る前提**なので、報告には Claude が読みやすい「差の範囲だけ切り出した前後」も出す。
- 終了コード: 0 = 差なし / 1 = 差あり / 2 = 撮影失敗あり。

## 8. 決まりとして根づかせる(今後作るものも沿うように)

1. **カタログ漏れの検査(テスト)**: vitest のテストで次を照合し、カタログに無い窓があれば落とす。
   - ModalShell・HousingPanelModal・MobileBottomSheet を使う部品の一覧
   - ルーター定義のルート一覧
   - 段階 2・3 で撮る予定のものは「後で撮る」の印を付けて許す(理由を必須にする)。
   - 既存の `ModalShell.guard.test.ts` と同じ考え方。
   - これで「新しい窓を足したらカタログにも足す」が機械的に強制される。
2. **ルール文書**: `.claude/rules/` に「リファクタ・見た目に関わる変更は、前後で visual-regress を回してから完了と言う」「新しい画面・窓はカタログに足す」を書く(編集時に自動で読まれる形)。
3. **既存道具との分担**: 表の位置・動作の細かい検査は `scripts/sticky-scroll/regress.mjs`、横スクロールの同時移動は `frame-sync.mjs`。visual-regress は「全画面の見た目」担当。表に触るリファクタでは両方回す。

## 9. 制約

- 公開リポ: 見本データ・見本画像に実ユーザーの情報や画像を入れない。撮った写真・報告は gitignore に入れる。
- 本番・Firestore に一切つながない(遮断を基本にし、許可リスト方式にする)。
- 写真は dev サーバーで撮る(store を直接触る開き方が dev 専用のため)。本番ビルドとの見た目の差は対象外。

## 10. 細部の決定(Claude の判断・事前レビューの質問への回答)

- **base 側の環境変数**: 一時 worktree は `.claude/worktrees/` の外(OS の一時フォルダ)に作り、`.env.local` をコピーする。実行が終わったら worktree ごと消す(シークレット走査の警告対象を増やさないため)。Firebase は遮断するので値の大半は効かないが、`VITE_MEDIA_PROXY_BASE_URL` など URL の形に効くものがあるので、ダミーではなく実ファイルをコピーする。
- **base に無いものが必要な場合**: base が古くて手順が通らない画面は「撮影失敗(base 側)」として報告に出す。黙って飛ばさない。
- **セレクタの書き方**: カタログの `open` / `ready` は、まず role・aria-label・既存の `data-tutorial`・表示文字列で書く(新旧どちらでも動く書き方)。`data-testid` を足すときは**それだけの独立したコミット**にして、リファクタを始める前に入れる。こうすれば base にも入る。
- **許容の数値**: 既存 `shots.mjs` の既定値(8×8 ブロック・平均色差 6・3 回撮って最大差 × 1.5・下限 0.05% かつ 10 ブロック)をそのまま使う。乱数を固定すれば MIL-SPEC のノイズ canvas も同じ絵になる見込み。それでも揺れる領域だけ、画面ごとに理由を書いてマスクしてよい(マスクは報告ページに一覧で出す)。
- **画像・動画**: 外部ホストの画像だけ差し替え、同梱のアセット(`public/` の webp・動画)はそのまま使う。背景動画は止めて撮る。ハウジング背景は 2026-10-26 の修正で「流れていない間は静止画」になったので、自然に静止画で撮れる。MIL-SPEC の背景動画は 0 秒で止める。
- **段階 1 の完了条件**: 次の 3 つがそろったら完了とする。
  - §5 の合格条件 1・2 を満たす
  - ログイン不要の画面と窓がカタログに入っている
  - カタログ漏れテストが通る(段階 2・3 の分は「後で撮る」印)
- **漏れテストの作り方**: 次の 2 つを静的に照合する。
  - 窓の殻(ModalShell・HousingPanelModal・MobileBottomSheet・ConfirmDialog)を import している部品
  - ルーター定義
  - 殻を使わない窓(ImportMenu などのポップ類・約 30)は、テスト内に手書きの一覧を持つ。新しく殻を使わない窓を作った場合はこの一覧に足す。漏れを完全に機械で拾うことは求めない。
- **終了コード**: 差ありと撮影失敗が混ざったら 2。報告にはどちらも載せる。
- **時間**: 15 分は、この PC(Windows・dev サーバー 2 つ・並列 3)での実測で判断する。超えたら次の順に削る。
  1. 窓の en
  2. /miti ページの 1920 を ja のみにする
  3. 法務ページの 390

## 11. 作る人に任せること

- エンジンの内部構成やファイル分割、並列数。
- 各窓の具体的な開き方のセレクタ(調査結果は会話ログにある。必要なら `data-testid` を足してよい=アプリ側の小さな変更として許可)。
- 見本 JSON・見本画像の中身(人工データであること、画面が「ふつうに使われている」見た目になる程度の量があること)。
- 報告ページの見た目(ローカルで開く道具なので凝らない)。
