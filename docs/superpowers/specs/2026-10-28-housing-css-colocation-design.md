# ハウジング CSS を「部品の隣」へ移す 設計書

- 日付: 2026-10-28
- 対象ブランチ: `milspec-polish`(worktree `.claude/worktrees/milspec-polish`)
- 決定者: masaya が方針を一任(10-28)、 本書の判断は Claude。 「Claude 判断」と書いた所は masaya が読んで違えば直す。

## 1. 何をするか・なぜ

`src/styles/housing/` に番号付きで並ぶ 71 本(計 11,226 行)の CSS を、 それを使う部品(.tsx)の隣へ移し、 部品が自分で `import './X.css'` する形にする。

なぜ: 今の番号分割は「元の 1 本の並び順を守るため」の途中形態。 部品を直す人は、 その部品の見た目がどの番号のファイルにあるか探す必要があり、 部品を消しても CSS が残る。 部品の隣にあれば「部品を開けば見た目もそこにある・部品を消せば一緒に消える」になる(プロの標準・この repo でも MIL-SPEC が既にこの形=`src/components/military/footer/milspecFooter.css` 等)。

成功 = 見た目が 1 画素も変わらず、 ハウジングの各部品の見た目がその部品の隣にあり、 新しい見た目を書く人が迷わない。

## 2. 目標 / 目標でないもの / 失敗とみなすもの

目標:
- ハウジング専用の CSS は、 それを描く部品の隣に置き、 その部品が読み込む。
- 共有(複数部品が使う土台)は `src/styles/housing/` に残すが、 「トークン・外枠・倍率」だけに絞る。
- ファイル同士の「後に書いた方が勝つ」頼みを無くし、 読み込み順が変わっても見た目が変わらない状態にする。
- その状態を機械で見張る(新しく書く人が崩せない)。

目標でないもの:
- CSS Modules への移行・class 名の変更(接頭辞 `housing-` で既に衝突しないため・書き換え量に見合わない)。
- 見た目の改善・余分な規則の掃除・トークン化の追加(見つけたら一覧に残すだけ)。
- 遅延読み込み(画面ごとに CSS を後から読む)への変更。
- 残り CSS(military.css・index.css・MitigationSheet.css)。 同じ方針で別の計画にする。

失敗とみなすもの(技術的に動いても不可):
- visual-regress の housing で 1 件でも差が出たまま進む。
- 規則が 1 つでも消える・二重になる。
- スマホ表示だけ崩れる(スマホ用の上書きを部品へ散らす時に起きやすい)。

## 3. 今の事実(調査済み・再調査不要)

- 入口 `src/styles/housing.css` は `@import` 71 行だけ。 読む部品は `HousingShell.tsx` / `HousingDetailPage.tsx` / `HousingEditPage.tsx` / `HousingerPage.tsx`。
- ハウジングの部品は `App.tsx` で通常 import(遅延読み込みでない)。 よってビルドでは CSS が 1 本にまとまり、 並びは「JS の import をたどった順」で決まる。
- `.housing-*` の class は 935 種類。 2 本以上のファイルにまたがるのは 120 種類だけ(多い組: 19 詳細↔21 ハウジンガー 8 / 56 お気に入り↔63 スマホ 8 / 19↔63 5 / 49 ライブ地図↔62 スマホ 5 …)。 残り 815 種類は 1 本の中で完結。
- 倍率 `68-scale-pc.css` は `html:root .x` で詳細度を上げてあり、 並び順に頼らない作り。
- 中央パネル用トークン `70-center-tokens.css` は `scripts/housing-scale/center-tokens.mjs` が **入口の @import をたどって全 CSS を読み** 生成する。 `convert.mjs` も同じく入口から全ファイルを読む。
- 入口を読むテスト: `src/lib/housing/__tests__/housingScaleCss.test.ts`(`readCssBundle` で入口を連結)・`src/data/housing/__tests__/wardMapNodeHiding.test.ts`(入口のパスを直接読む)。
- 書き方の決まり `.claude/rules/housing-design.md` 66 行目は「`src/styles/housing/` の該当ファイルに書く」。 `ui-design.md` / `DESIGN.md` は `src/styles/housing/**` を対象外にしている(ハウジングの部品フォルダは `src/components/housing/**` で既に対象外)。
- 確認の道具: `scripts/visual-regress/`(housing 110 件・基準 dpr2 は 10-28 撮り直し済)・`src/architecture/__tests__/file-size.test.ts`(500 行の見張り)。

## 4. 決めたこと

### 4.1 置き場所と名前(Claude 判断)
- その見た目の「持ち主」の部品と同じフォルダに、 **部品と同じ名前**で置く(例: `src/components/housing/tour/TourNavPage.tsx` の隣に `TourNavPage.css`)。 MIL-SPEC の小文字始まりとは違うが、 ハウジングは「部品名で探せる」方を取る。
- 持ち主 = その class を JSX に書いている部品(同じ class を 2 部品が書くなら、 その要素の外側の枠を描く方)。 1 つの番号ファイルが複数の部品の見た目を含むなら、 部品ごとに分ける(1 ファイル 1 仕事)。
- 複数の画面で使い回す部品(例: カード・窓の殻)の見た目は、 その部品の隣に置く。 画面側が「その画面の中だけ」変える規則は、 詳細度が上がる書き方(親 class を前に付ける)なら画面側に置いてよい。 同じ詳細度で上書きしている規則は、 部品側のファイルへ移して部品側で条件(親 class)を付ける。
- 言語別の規則(`:lang()` / `[data-lang]`)はハウジングの CSS に無い(調査済み)。
- 部品の .tsx の先頭の import 群に `import './X.css';` を 1 行足す。 部品は他の場所で無条件に読み込まれている前提なので、 読み込みの有無で表示が変わることはない(ただし「どの部品からも読まれない CSS」が出たら止まって確認)。

### 4.2 共有に残すもの(Claude 判断)
`src/styles/housing/` に残すのは次だけ:
- トークン(`00-tokens.css`)
- 外枠(`01-shell-frame.css`・`27-rebuild-shell.css`。 画面全体の枠・背景・ヘッダー周り)
- 倍率(`68-scale-pc.css`・`69-scale-svg-icons.css`・`70-center-tokens.css`)
- 実装中に「3 つ以上の部品が同じ規則を共有していて持ち主が決められない」と分かったものは、 `src/styles/housing/` に意味の名前で新しいファイルを作って置いてよい(番号は付けない)。 何を共有に回したかは計画の一覧に理由つきで残す。

入口 `housing.css` は残った共有ファイルの `@import` だけにする。 番号は外して意味の名前にし(`tokens.css` `shell-frame.css` …)、 並び順はそのまま守る(この中だけは順番が意味を持つ)。

### 4.3 順番に頼らない形にする(本設計の要)
部品が自分で読み込むと、 ファイル同士の並びは import のたどり方次第になり、 今の番号順は保証されない。 そこで:
- **他のファイルにある規則を上書きしている規則は、 上書きされる側(持ち主)のファイルに、 元の規則より後ろへ移す。** これで「同じ要素・同じ詳細度・同じ性質」の規則はすべて 1 本のファイルの中に並び、 ファイルの並び順が結果に影響しなくなる。
- 例外: 親の状態で子の見た目を変える規則(例: `.housing-x.is-open .housing-y`)は詳細度が上がるので順番に頼らない。 これは置きやすい方(普通は親)に置いてよい。
- スマホ用の上書き(`62-mobile-layout.css`・`63-mobile-tour-bars-sheets.css`・`61-mobile-shell.css` の `@media (max-width: 767px)` 塊)は、 規則ごとに持ち主の部品ファイルの**末尾**へ `@media` ごと移す。 外枠のスマホ規則は外枠ファイルの末尾へ。
- 共有ファイル(トークン・外枠・倍率)と部品ファイルの間で、 同じ詳細度の上書きが残る場合は、 共有ファイルが常に先に読まれることを保証する: `HousingShell.tsx` など入口を読む部品で、 `housing.css` の import を他の部品の import より上に書く(`HousingDetailPage.tsx` など入口を読む他の部品も同じ)。 保証できているかは 4.4-2 の道具がビルド CSS の前後で確かめる。 崩れたら import の並びの方を直す(外枠の規則は部品へ移さない)。

### 4.4 確認方法(機械で判定できるもの)
各まとまりを移すたびに次の 4 つを全部通す。 1 つでも落ちたら次へ進まない。
1. **規則の欠け・重複なし**: 変更前と後のビルド CSS(ハウジング分)を「規則(セレクタ+@media+宣言)の集まり」として比べ、 並び以外が一致すること。 比べる道具を最初に作る(`scripts/` 配下・一時でなく残す)。
2. **順番頼りの検出と順序保存**(Claude 判断で範囲を決定): 「順番頼りの組」= 違うソースファイルにある 2 規則で、 ①同じ @media 条件 ②詳細度が同じ ③対象(セレクタ右端の複合セレクタ)に共通の class がある ④同じ性質を宣言する、 の 4 つを満たすもの。 完全一致だけでなく `.x .y` と `.z .y` のような「同じ要素に当たりうる同詳細度」も拾う(要素が実際に重なるかまでは判定しない=取りこぼすより拾いすぎる側に倒す)。
   - 部品ファイル同士の組 = 移行の終わりに 0。
   - 共有ファイル(トークン・外枠・倍率)と部品ファイルの組 = 0 にできなくてよいが、 **ビルド CSS 上の前後が移行前と同じ**であること(共有が先)を道具が確かめる。 外枠の規則は共有に残す(部品へ移さない)。
   - これは恒久テストにして、 後から書く人が部品同士の順番頼りを持ち込んだら落ちるようにする。
   - 比べるのは minify 前の CSS(ソース群を PostCSS で読む)にする。 minify による宣言の統合で判定がぶれないため。
3. **見た目**: `scripts/visual-regress` の housing 110 件が基準と一致。 開いた状態・窓・スマホが全部撮れているわけではないので、 見た目の安全は主に 2 の「順番頼りの組の前後が変わらない」で担保し、 110 件はその裏付けとする。 計画では、 またがり class を持つ部品のうち 110 件に写らない状態を一覧にし、 撮れるものは catalog(`scripts/visual-regress/catalog/housing.mjs`)に足してから移す。
4. ビルド 0・関係テスト通過・500 行の見張り通過。

### 4.5 道具・テスト・決まりの追従
- `center-tokens.mjs` と `convert.mjs` は「入口の @import」ではなく「ハウジングの CSS 全部」(共有フォルダ+`src/components/housing/**/*.css`)を読むよう直す。 生成結果 `70-center-tokens.css` が移行前後で一字一句同じことを確認。
- 入口を読むテスト 2 本は、 規則の在りかに合わせて読む先を直す(`wardMapNodeHiding` は地図部品の CSS へ・`housingScaleCss` は倍率ファイルへ)。 テストの意図(何を固定しているか)は変えない。
- 見張りを足す: `src/components/housing/` の .css は同じフォルダの .tsx のどれかが import していること(置き去り防止)/ `src/styles/housing/` に許可一覧以外の新しいファイルを置いたら落ちる(許可一覧はテスト内の配列。 足す時は 1 行ごとに「なぜ共有か」のコメント必須・それ以上の手続きは無し=Claude 判断)。
- `.claude/rules/housing-design.md` の置き場所の段落を「部品の隣に部品と同じ名前で置き、 部品が import する。 共有はトークン・外枠・倍率だけ。 他部品の見た目を同じ詳細度で上書きしない」に書き換える。 frontmatter の対象パスに `src/components/housing/**/*.css` は既に含まれる(`src/components/housing/**`)。

### 4.6 進め方
- 画面のまとまりごとに 1 コミット(例: 探す画面 / 登録 / 詳細 / ツアー / ハウジンガー / 窓・小物 / スマホ上書きの散らし)。 まとまりの切り方と順番は計画で決める。 推奨は「またがりの少ないまとまりから」で、 スマホ上書き(62・63)は最後にまとめて散らす。
- 各コミットで 4.4 の 1〜4 を通す。 visual-regress は housing だけ(約 110 件)で回す。
- 計画には「番号ファイル 71 本 → 移し先(部品ファイル名 or 共有)」の一覧を全件載せる。 120 種類のまたがり class も、 どこへ寄せるかを全件載せる。

## 5. 作る人に任せること
- 番号ファイル内の規則を部品ごとに分ける細かい線引き(4.1 の「持ち主」の定義に沿う限り)。
- 4.4 の 1・2 の道具の作り(PostCSS で読むなど)。 ただし「ソースファイル名」を規則ごとに持てる形にすること(ビルド CSS だけでは元ファイルが分からないので、 ソースの CSS 群を読む・または sourcemap を使う)。
- 1 つの部品の CSS が 500 行を超える場合の分け方(部品の中の意味のまとまりで分け、 同じフォルダに置く)。

## 6. 宿題・既知のこと
